# japanese-writing-gemini

日本語の人間向け文書を書く前に、Geminiへの委任を提案するエージェント用スキルです。オーナーの明示承認後、正本から確認した事実をまとめ、Geminiが完成文書全体を書き下ろすためのコピー用ブリーフを表示します。

Geminiへの送信や接続は行いません。ブリーフをコピーして渡すところから先は、オーナーが扱います。Geminiの特定モデルや、日本語品質の優劣を前提にするスキルではありません。

## 対象

公開README、記事・ブログ、技術ドキュメントを含む公開文書、製品紹介文など、人間が読むまとまった文書が対象です。紹介部分に限らず、仕様や操作手順の説明、見出し、表、コードブロック、コマンド例を含む文書全体を委任候補にできます。

AI向けの指示・引き継ぎ、オーナー向け報告・レビュー、短いUI文言、コードコメント、コミットメッセージ、単純な誤字修正は対象外です。詳しい判定と承認の規則は [SKILL.md](SKILL.md) が正本です。

## 書き下ろしと事実の確認

Geminiは既存の文章表現をテンプレートにせず、事実確認用に使い、文書を最初から書き下ろします。見出しや表、技術ブロックも新しく構成できます。

元のエージェントは、技術的事実、コマンド名・オプション・実行条件、ファイルパス、APIキーの扱い、ライセンス、セキュリティ条件を正本から確認し、必要な材料をブリーフ内に同梱します。Geminiはその事実や条件を変更・発明しません。秘密値は含めず、例には安全なプレースホルダーを使います。

## 使い方

1. エージェントに、対象となる文章の作成や改稿を依頼します。
2. エージェントが本文の執筆前に「Geminiに任せる候補」と提案し、承認を待ちます。資料調査は続けられます。
3. 「Gemini用のブリーフを書いて」などと明示的に承認すると、一つのコードブロックにまとまったブリーフが表示されます。

「Geminiのほうがよさそう」という感想だけでは作成を開始しません。対象を指定して最初からブリーフ作成を依頼した場合は、再確認なしで材料を調べます。表示後の送信、ファイル変更、公開、Geminiの回答のレビュー・適用はこのスキルに含まれません。

## Geminiから返ってきた後

返却後の確認は、このスキルの範囲外の別作業です。オーナーが元のエージェントに依頼した場合は、文章全体を再執筆せず、事実誤認・コマンド・安全性・ライセンスの問題に必要な最小修正を行う運用を想定しています。構成や表現を元のREADMEへ戻す作業にはしません。表示されたブリーフだけで返却文の検証・適用まで済んだことにはならず、適用や公開は別作業の依頼範囲に従います。

## エージェントへの読み込ませ方

本体は [SKILL.md](SKILL.md) です。先頭の名前・説明を除く手順は素のMarkdownで、専用API、MCP、コマンド、環境変数、他のスキルへの依存はありません。

スキル機構のないエージェントでも、次のどちらかで利用できます。

- 会話にSKILL.mdの本文を貼り付け、「今後、対象文章を扱うときはこの手順に従って」と伝える。
- エージェントが読むルールファイルに、次のような参照を追加する。パスは実際の配置に合わせる。

```text
日本語のまとまった人間向け公開文書（README・技術ドキュメント・記事など）を新規作成・大幅改稿するときは、執筆前に skills/japanese-writing-gemini/SKILL.md を読み、その対象判定・提案・承認の手順に従う。
```

ファイルを参照できないエージェントでは貼り付け方式を使い、執筆の根拠資料も与えてください。読み込まれていないルールや参照先を、このスキル自身が有効化することはできません。

### Codexの補足

プロジェクト内なら `.agents/skills/japanese-writing-gemini/` にSKILL.mdと任意のagentsフォルダを配置します。自動選択を許可する設定を [agents/openai.yaml](agents/openai.yaml) に同梱しています。明示的に使う場合は `$japanese-writing-gemini` を指定できます。配置と自動選択は [公式のスキル説明](https://learn.chatgpt.com/docs/build-skills) を参照してください。

### Claude Codeの補足

プロジェクト内なら `.claude/skills/japanese-writing-gemini/SKILL.md` に配置します。本体には自動選択を無効にする `disable-model-invocation: true` を加えません。明示的に使う場合は `/japanese-writing-gemini` を指定できます。agents/openai.yamlは不要です。[公式のスキル説明](https://code.claude.com/docs/en/skills) を参照してください。

自動選択はモデルとホストの設定に依存します。有効化は、すべての該当依頼で必ず発火する保証ではありません。導入後は下の利用例で、本文より先に提案することと、承認前にブリーフを出さないことを確認してください。

## 利用例

以下は架空の依頼による使い方の例です。実際のブリーフには、そのプロジェクトで確認できた事実を使います。

### 1. README全体を書き下ろす

オーナー: 「このアプリのREADMEを、初めて見る人に伝わるように書き直して」

エージェントはREADME全体についてGeminiへの委任を提案します。本文を書かずに承認を待ち、機能・制約・コマンド・設定・ライセンスをコードや正本の文書と照合できます。

オーナー: 「README全体をGeminiに任せよう。ブリーフを書いて」

確認済み材料を同梱し、既存表現をテンプレートにせず文書全体を書き下ろすブリーフを表示して終了します。Geminiは見出しや表、操作手順の説明やコマンド例も構成できますが、確認済みのコマンド・設定条件・ライセンス条件を変えたり、未確認の使い方を補ったりはしません。

### 2. 開発背景のブログ用ブリーフを直接依頼する

オーナー: 「開発メモをもとに、利用者向けの開発背景記事を書くGemini用ブリーフを作って」

ブリーフ作成が明示されているので、再承認は求めません。公開可能なメモから、開発の理由と確認済みの経緯を整理します。書かれていない苦労話や利用者の声を補わせず、記事全文の書き下ろしを依頼するパックを表示します。

### 3. 公開する技術ガイドとオーナー向け報告を同時に依頼する

オーナー: 「APIキーの設定から初回実行まで、公開する利用ガイドを書いて。それと、未解決の不具合を私に報告して」

エージェントは利用ガイドについて提案して停止します。不具合報告は通常どおり、根拠と未確認を保って書きます。

オーナー: 「文章はGeminiのほうがよさそう」

利用ガイドの承認待ちを維持し、本文もブリーフも出しません。「利用ガイドをGeminiに任せるブリーフを作って」と続いた時点で、APIキーの扱いと確認済みの実行手順を同梱したブリーフを作成します。実際のキーは含めず、不具合報告の委任にも範囲を広げません。
